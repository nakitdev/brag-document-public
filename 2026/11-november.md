### 2026-11-02 (จันทร์)

**ทำอะไรไป**
- ทำใบปะหน้าขนส่งรายใหม่ขนาด 100x150 และ 100x180 ครบ 3 แบบแสดงสินค้า + เก็บเงินปลายทาง สองขนาดใช้ layout เดียวกัน แล้ว merge เข้า develop
- แยกการตัดหมายเหตุ 1–3 บรรทัดเป็นฟังก์ชันให้ 100/150/180 ใช้ร่วมกัน
- ทำหลักฐานประกอบการลบโฟลเดอร์ใน cloud storage 3 โฟลเดอร์ให้ SRE
  - 2 โฟลเดอร์: route ที่เขียนลงไปถูกถอดและขึ้น prod แล้ว ไม่มี repo ไหนอ้างถึง → ลบได้
  - 1 โฟลเดอร์: service บน prod ยังเขียนทุกครั้งที่สร้างใบปะหน้า → ห้ามลบ เสนอ lifecycle rule ลบไฟล์เก่าแทน
- เข้า refinement

**ผลลัพธ์ / impact**
- ใบปะหน้าขนส่งรายใหม่ทำครบ 4 จาก 5 ขนาด อยู่บน develop แล้ว
- กันไม่ให้ลบโฟลเดอร์ที่ระบบพิมพ์ใบปะหน้าบน prod ยังใช้อยู่ ถ้าลบไป ลิงก์ดาวน์โหลดใบปะหน้าจะพังทันที

**สื่อสารกับทีม**
- อัปเดตการ์ดงานใบปะหน้า แจ้งทีม และแจ้ง SRE พร้อมหลักฐานและข้อเสนอ lifecycle rule (รวม 3 ครั้ง)

**ได้เรียนรู้**
- ก่อนเสนอลบโฟลเดอร์ใน cloud storage ต้องดู config prod ด้วย ไม่ใช่แค่ค้นชื่อ path ในโค้ด เพราะ path อาจมาจากค่า default ของ env (`process.env.X ?? "default/path"`) ที่ prod ไม่ได้ override
- ถ้าแบบของสองขนาดเหมือนกัน ต่างกันแค่ความยาว ใช้ฟังก์ชันเดียวแล้วคำนวณจำนวนรายการจากพื้นที่ที่เหลือ ดีกว่าแยกไฟล์

### 2026-11-04 (พุธ)

**ทำอะไรไป**
- ทำใบปะหน้าขนาด 57x100 ตามแบบ Figma แล้ว merge เข้า develop
  - ความยาวใบยืดตามเนื้อหา สูงสุด 19 รายการ + "และอีก N รายการ" และหมายเหตุ 7 บรรทัด
  - แก้หมายเหตุสั้นที่ล้นไปหน้าที่สอง (เผื่อที่ให้บรรทัดสุดท้ายตอนคำนวณความสูงหน้า)
- เปลี่ยน barcode ทุกขนาดจากรูป JPEG ที่ยืดจนเบลอ เป็นแท่ง vector วาดลง PDF ตรงๆ
- ทุกขนาด: ชื่อผู้ส่งตัดให้อยู่บรรทัดเดียว ไม่ทับกล่องผู้รับ
- เทสบน beta แล้ว เจอปัญหาฝั่ง API ขนส่งเมื่อมีสินค้า 15+ รายการ แจ้งทีมที่ดูแล
- เขียน postmortem เสร็จ

**ผลลัพธ์ / impact**
- ใบปะหน้าขนส่งรายใหม่ครบทั้ง 5 ขนาดอยู่บน develop
- barcode คมทุกขนาด ลดความเสี่ยงที่ขนส่งสแกนไม่ติด
- unit test 249 ข้อ ผ่านหมด

**สื่อสารกับทีม**
- อัปเดตการ์ด แจ้งทีมเรื่อง postmortem และผลเทส (รวม 4 ครั้ง)

**ได้เรียนรู้**
- ลำดับการวาดใน PDFKit สำคัญ: รูปที่มีพื้นขาว (QR) วาดทีหลังจะทับเส้นกรอบ ต้องวาดรูปก่อนแล้วค่อยวาดเส้น
- barcode ที่เป็นรูปแล้วยืดจะเบลอ ใช้ `encodings` ของ JsBarcode มาวาดเป็น rect แทนจะคมทุกขนาด
- `heightOfString` ที่มี `lineGap` ติดลบให้ค่าน้อยกว่าที่บรรทัดสุดท้ายต้องใช้จริง ถ้าความสูงหน้าไม่พอ PDFKit จะขึ้นหน้าใหม่เอง
- ก่อนตีความ requirement ("ความยาวไม่จำกัด") ให้เทียบกับตัวอย่างในแบบก่อน

### 2026-11-05 (พฤหัสบดี)

**ทำอะไรไป**
- แก้ใบปะหน้าตาม code review แล้ว merge เข้า develop และ master
  - QR ใช้เลขพัสดุอย่างเดียว · เอา fallback ไป layout เดิมที่ไม่มีทางถูกเรียกออก · หมายเหตุว่างพิมพ์ "-" ทุกขนาด
  - ฟังก์ชันตัดข้อความให้พอดีกล่อง เปลี่ยนจากตัดทีละตัวอักษรเป็น binary search
  - test ใช้ `jest.spyOn` แทนการแทนที่ prototype ที่ทำให้ test ผ่านหลอก
  - ขนาด 100 แบบบรรทัดเดียว ใช้ที่ว่างลงไปถึงหมายเหตุ ไม่ล็อกไว้ 2 บรรทัด
- หาต้นเหตุที่ "…" โผล่ก่อนบรรทัดสุดท้ายของรายการสินค้า: PDFKit 0.18 ตัดสินใจใส่ ellipsis โดยไม่นับ `lineGap` ติดลบ จึงพังเมื่อความสูงกล่องตกในช่วง 3 pt ที่เกิดซ้ำทุก 13 pt แก้ด้วยการขยายกล่องไม่เกิน `-lineGap`

**ผลลัพธ์ / impact**
- ใบปะหน้าขนส่งรายใหม่ทั้ง 5 ขนาดเข้า master
- ร้านที่มีสินค้าหลายร้อยรายการไม่ค้าง: วัดความสูงข้อความจาก 12,337 ครั้ง เหลือไม่ถึง 40 ครั้ง ไม่บล็อก event loop
- รายการสินค้าไม่มี "…" กลางรายการอีก test ไล่ความสูงกล่อง 20–120 pt ทุก 0.5 pt
- unit test 277 ข้อ ผ่านหมด

**สื่อสารกับทีม**
- แจ้งทีมเรื่อง deploy และอัปเดตสถานะการ์ด (รวม 2 ครั้ง)

**ได้เรียนรู้**
- PDFKit ใส่ ellipsis เมื่อเหลือที่ไม่พอ 2 บรรทัด โดยวัดบรรทัดแบบไม่รวม `lineGap` ถ้า `lineGap` ติดลบจะใส่เร็วไปหนึ่งบรรทัดในบางความสูง ต้องไล่ทดสอบหลายความสูง ไม่ใช่ค่าเดียว
- ความยาวข้อความกับความสูงเป็นฟังก์ชันที่เพิ่มขึ้นทางเดียว จึงใช้ binary search หาจุดตัดได้
- mock ด้วยการแทน prototype ใน `beforeEach` ทำให้ test ผ่านหลอกได้ ใช้ `jest.spyOn` + `restoreAllMocks` แทน
- ลองแก้โค้ดให้ผิดโดยตั้งใจ (mutation check) เพื่อยืนยันว่า test ใหม่จับบั๊กได้จริง
